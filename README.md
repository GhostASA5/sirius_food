# Сириус.Еда

Учебный FastAPI-проект восстановлен из приложения А лабораторной работы № 2. История Git содержит отдельные коммиты для лабораторной № 2 и практической № 3.

## Лабораторная работа № 2

Модули `orders` и `users` разделены на `router.py`, `service.py` и `repository.py`. Запрос проходит через роутер, сервис и репозиторий к PostgreSQL. Сервис получает репозиторий через конструктор и не импортирует FastAPI или SQLAlchemy. Создание заказа и списание баланса выполняются в одной транзакции. Маршруты, структуры ответов и коды ошибок MVP были сохранены в коммите лабораторной работы.

## Практическая работа № 3

Регистрация сохраняет bcrypt-хеш пароля и назначает роль `student`. `/auth/login` выдаёт access-токен на 15 минут и refresh-токен на 7 дней. Хеш refresh-токена хранится в БД, `/auth/refresh` выдаёт новый access-токен после проверки записи. JWT содержит тип токена, поэтому refresh-токен нельзя использовать для доступа к заказам.

Для входа в защищённый маршрут клиент передаёт `Authorization: Bearer <access_token>`. `get_current_user` проверяет подпись, срок действия, тип токена, существование пользователя и блокировку. `require_role` проверяет роль в API-слое. Сервисы заказов, пользователей и доставок проверяют право на конкретный объект. Отсутствующий токен даёт 401, чужая роль или объект — 403.

`POST /orders/create` берёт пользователя из JWT; `user_id` отсутствует в теле запроса. `POST /orders/{order_id}/cancel` доступен владельцу заказа, `GET /orders/kitchen/orders` — повару. Изменение меню доступно администратору и повару. `GET /delivery/mine` показывает курьеру только его доставки; `GET /delivery/{delivery_id}` доступен назначенному курьеру, владельцу заказа и администратору. Назначение курьера доступно администратору, завершение доставки — назначенному курьеру. Пополнение баланса доступно только владельцу. Регистрация остаётся публичной, чтобы новый пользователь мог получить учётную запись.

## Лабораторная работа № 4

`GET /menu/items` читает меню через Cache-Aside в `MenuRepository`: ключ `menu:all`, TTL 300 секунд. `GET /menu/categories/{id}` использует ключ `menu:category:{id}` с TTL 600 секунд. Категории добавлены миграцией `0003_menu_categories`; администратор и повар могут создать категорию через `POST /menu/categories` и передать `category_id` при создании или изменении блюда. После записи репозиторий удаляет затронутые ключи. При одновременном промахе используется блокировка Redis и повторная проверка кеша. Если Redis недоступен, чтение идёт из PostgreSQL. На старте приложение прогревает `menu:all`.

## Лабораторная работа № 5

После сохранения заказа `OrderService` передаёт событие адаптеру `CeleryOrderNotifications`. Он ставит три задачи в Redis: имитацию генерации PDF (2 секунды), отправки email (1 секунда) и SMS (1 секунда). Реальная генерация файла и подключение к почтовому или SMS-провайдеру в задании не предусмотрены. Воркеры выполняют задачи отдельно от HTTP-процесса. Для email, SMS и PDF настроены до трёх повторов с экспоненциальной задержкой. Ключи `order_task:{kind}:{order_id}` в Redis предотвращают повторную обработку в течение часа. После исчерпания повторов задача записывается в список `dlq` базы Redis 0.

На локальном API созданы два отдельных тестовых заказа. Результаты замера находятся в [benchmarks/order_latency.csv](benchmarks/order_latency.csv): синхронная имитация заняла 4023,51 мс, ответ после внедрения Celery — 42,62 мс. Логи воркера подтвердили выполнение всех трёх задач для второго заказа. Для демонстрации ошибки email каждого пятого заказа можно временно задать `SIMULATE_EMAIL_FAILURES=true` в окружении воркера; по умолчанию эта имитация выключена.

```bash
docker compose up --build -d app worker delivery
docker compose logs -f worker
docker compose exec redis redis-cli -n 0 LRANGE dlq 0 -1
```

## Практическая работа № 6

Модуль доставки вынесен в отдельный gRPC-процесс `delivery`, который работает с теми же моделями и PostgreSQL. Контракт находится в [proto/delivery.proto](proto/delivery.proto). HTTP-маршруты доставки в основном приложении используют gRPC-клиент для назначения курьера, завершения доставки, получения доставки и списка доставок курьера. Клиент передаёт access-токен в metadata; gRPC-сервис самостоятельно проверяет JWT, роль и право на конкретную доставку. При недоступности сервиса HTTP API отвечает 503, при превышении срока ожидания — 504.

`TrackDelivery` реализует Server Streaming: после проверки доступа отправляет `in_progress`, `on_the_way`, `delivered` с интервалом две секунды. Это демонстрационный поток: промежуточные статусы не сохраняются в БД. Статус `delivered` записывается через `CompleteDelivery`. Посмотреть поток для существующей доставки можно из контейнера приложения:

```bash
docker compose exec app python -m scripts.track_delivery 1
```

Команда запросит access-токен пользователя, имеющего доступ к доставке. Номер `1` замените на фактический ID доставки. В существующем проекте нет маршрута оплаты заказа; для назначения курьера заказ должен уже иметь статус `paid`. Генерация Python-кода из `.proto` выполняется при сборке Docker-образа и в CI командой `python -m scripts.generate_proto`.

## Практическая работа № 7

`POST /orders/{order_id}/pay` доступен владельцу заказа и администратору. Заказ создаётся в статусе `processing`; при оплате переходит в `paid`. Баланс списывается при создании заказа, поэтому повторного списания при оплате нет. Переход статуса и запись `OrderPaid` в таблицу `outbox` выполняются одной транзакцией. Отдельный процесс `outbox` публикует ожидающие события в topic exchange `sirius_events` и помечает их отправленными после подтверждения RabbitMQ.

Ключ `order.paid` направляет событие в независимые `kitchen_queue` и `delivery_queue`. Кухня создаёт одну запись в `kitchen_orders`; сервис доставки назначает свободного курьера и создаёт доставку. Каждый обработчик записывает `(event_id, consumer)` в `processed_events` в одной транзакции со своим результатом. Повторная доставка события не создаёт дублей. При ошибке обработки сообщение повторяется до трёх раз, затем попадает в соответствующую очередь `kitchen_dlq`, `delivery_dlq` или `compensation_dlq`. Невалидный JSON попадает в DLQ сразу. Для обработки аварийных сообщений используется `dlx_exchange`.

Если свободного курьера нет, обработчик доставки записывает `DeliveryFailed` в outbox. Очередь `compensation_queue` получает его по ключу `delivery.failed`: заказ отменяется, ранее списанная сумма возвращается на баланс, запись кухни помечается отменённой, а `OrderCancelled` записывается в outbox и публикуется в `order_cancelled_queue`. Повторное событие не возвращает деньги второй раз. Сумма заказа сохраняется при создании; для старых заказов без этого поля используется сумма из события оплаты.

Запуск из каталога `sirius_food`:

```powershell
docker compose up --build -d
docker compose ps
```

RabbitMQ Management доступен по `http://localhost:15672` с логином `sirius` и паролем `sirius`. После `POST /orders/create` вызовите `POST /orders/{order_id}/pay` с access-токеном владельца заказа. Для автоматического назначения нужен зарегистрированный пользователь с ролью `courier` без активной доставки. Проверить обработчики можно командами `docker compose logs -f outbox kitchen delivery_worker compensation` и `docker compose exec db psql -U sirius -d sirius_food -c "SELECT id, routing_key, published_at FROM outbox ORDER BY id DESC LIMIT 10;"`.

Интеграционный тест `tests/test_events.py` отправляет корректное событие дважды и невалидный JSON через настоящий RabbitMQ, затем проверяет одну запись кухни и попадание повреждённого сообщения в DLQ. Другие тесты проверяют доставку и компенсацию. Локально прошёл 31 тест; проверка через Docker подтвердила создание заказа кухни и доставки после оплаты. При остановленном RabbitMQ оплата заказа 9 прошла, событие осталось в outbox и после запуска брокера было опубликовано и обработано.

## Учебная практика — трек C «Полнотекстовый поиск»

`docker compose up --build -d` запускает Elasticsearch и процесс `search_worker`. PostgreSQL остаётся источником меню. При старте обработчик создаёт индекс `menu` и загружает блюда через `python -m scripts.reindex_menu`; изменения блюд записываются в outbox и поступают через RabbitMQ в `search_queue`. Повторная индексация по ID блюда не создаёт дублей. Ошибки после трёх повторов направляются в `search_dlq`.

`GET /search?q=сырники&category=Завтраки&min_price=100&max_price=200&page=1&size=20` ищет по названию и описанию, фильтрует доступные блюда по категории и цене, возвращает пагинацию, оценки релевантности и фасеты категорий и цен. `GET /search/suggest?q=сыр` возвращает до десяти названий. Русский анализатор учитывает словоформы, fuzzy-поиск допускает опечатки; точное совпадение названия и совпадение фразы имеют повышенный вес. Поле `description` добавлено в меню. При недоступности Elasticsearch API отвечает 503. Решение и компромиссы описаны в [ADR](docs/ADR-001-search.md).

Для воспроизводимого сравнения выполните `docker compose exec app python -m scripts.benchmark_search`. На двух исходных блюдах и 100 последовательных запросах SQL LIKE дал среднее 0,939 мс и p95 2,107 мс, Elasticsearch — среднее 9,991 мс и p95 13,753 мс. Это замер малого набора на данной машине, а не вывод о производительности на сотнях блюд. Сквозная проверка создания и изменения «Сырников с творогом» подтвердила обновление индекса, фильтр по категории и цене и автодополнение.

## Учебная практика — трек A «Промокоды и программа лояльности»

Из каталога проекта выполните `docker compose up --build -d`. API применяет миграцию `0007_loyalty`. Контейнер `loyalty_worker` обрабатывает события RabbitMQ, а Celery Beat каждый час ставит задачу деактивации просроченных промокодов. При применении промокода сроки также проверяются сразу.

1. Администратор создаёт код через `POST /promos`. Например, тело запроса `{"code":"STUDENT10","discount_type":"percent","discount_value":"10","valid_from":"2026-11-17T00:00:00Z","valid_until":"2027-01-01T00:00:00Z","max_uses":20,"min_order_amount":"100","once_per_user":true}`. Для денежной скидки используйте `discount_type: "fixed"`. Активность меняется через `PATCH /promos/{code}` с телом `{"is_active":false}`.
2. Покупатель создаёт заказ через `POST /orders/create` с телом `{"item_id":1,"quantity":1,"promo_code":"STUDENT10"}`. Поле промокода необязательное. Денежный баланс при создании должен покрывать сумму после скидки.
3. Для оплаты вызовите `POST /orders/{id}/pay`. В теле можно передать `{"points":"2.50"}`. Один балл заменяет один рубль, списать можно до 50% суммы после скидки. Эквивалент списанных баллов возвращается на денежный баланс, так как денежный резерв был списан при создании заказа. Без тела маршрут работает как раньше.
4. `GET /loyalty/me` показывает баланс, сумму начислений за вычетом отзывов и уровень. Bronze начисляет 3%, Silver — 5%, Gold — 7% от фактически оплаченной деньгами суммы. Пороги Silver и Gold по умолчанию равны 100 и 500 баллам, их можно настроить в `.env` через `LOYALTY_SILVER` и `LOYALTY_GOLD`. После отзыва начисления уровень пересчитывается. Если начисленные баллы уже потрачены, возможен отрицательный баланс до следующих начислений.

### Хранение и отмена

Счёт, операции с баллами, скидка и итог заказа используют `Numeric` и расчёты с `Decimal` до сотых. Денежный кошелёк использует существующее поле `Float`, поэтому итог при записи в него преобразуется обратно в `float`. При выдаче скидки строка промокода блокируется до записи заказа и факта использования. При отмене через API или после сбоя назначения курьера денежный возврат и запись `OrderCancelled` в Outbox выполняются в одной транзакции. Отдельные обработчики RabbitMQ возвращают списанные баллы, отзывают начисление и восстанавливают использование промокода. Повторы защищены ключами операций, а запоздалое `OrderPaid` для уже отменённого заказа пропускается. Обоснование описано в [ADR](docs/ADR-002-loyalty.md).

Для просмотра обработки выполните `docker compose logs -f loyalty_worker beat worker`. Тесты трека запускаются командой `python -m pytest tests/test_loyalty.py`.

### Нагрузка на промокод с одним использованием

Запускайте проверку на тестовой базе. Скрипт `scripts.prepare_promo_load` создаёт 1000 покупателей, блюдо и промокод с `max_uses=1`. Locust отправляет по одному запросу от каждого покупателя после общего сигнала старта. Установите зависимости из `requirements-load.txt`, затем выполните в PowerShell из каталога проекта:

```powershell
$env:PROMO_LOAD_FIXTURE = Join-Path ([IO.Path]::GetTempPath()) ('sirius-promo-' + [Guid]::NewGuid().ToString() + '.json')
try {
    docker compose exec -T app python -m scripts.prepare_promo_load | Set-Content -Encoding utf8NoBOM -LiteralPath $env:PROMO_LOAD_FIXTURE
    locust -f locust_promo.py --headless -u 1000 -r 1000 --run-time 90s --host http://127.0.0.1:8000 --only-summary
} finally {
    Remove-Item -LiteralPath $env:PROMO_LOAD_FIXTURE -ErrorAction SilentlyContinue
}
```

Контрольный запуск на отдельной базе PostgreSQL дал 1 успешное применение и 999 ответов «Промокод исчерпан», без других ответов. В БД подтверждены `current_uses = 1` и одна запись использования. Среднее время ответа составило 4,27 с, p95 — 8,4 с для одновременного старта 1000 пользователей.
