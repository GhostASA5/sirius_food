# Практическая работа 10

## Установка и тесты

Запустите Docker и установите зависимости командой `pip install -r requirements-test.txt`. Затем выполните `python -m pytest tests/integration tests/contracts -v`.

Testcontainers запускает PostgreSQL 15 с новым контейнером и случайным портом. Alembic применяет все миграции. Каждый тест работает внутри внешней транзакции с savepoint, поэтому commit внутри репозитория не переносит данные в следующий тест. Тесты используют настоящий JWT и HTTP → Service → Repository → PostgreSQL. Отправка уведомлений Celery и Redis-кеш заменены в фикстуре, чтобы проверка PostgreSQL не зависела от остальной инфраструктуры.

В Windows с Docker Desktop при необходимости задайте `$env:TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE='/var/run/docker.sock'`. Версия Testcontainers закреплена на 4.10.0, на которой проверены запуск и очистка контейнеров.

API проекта возвращает 200 при создании заказа и определяет покупателя по access-токену. Интеграционный тест проверяет эти действующие условия, сохранение заказа, списание денег, атомарный Outbox при оплате и отказ без изменения данных при недостаточном балансе.

## Контракт Pact

Для 9 баллов выбран вариант А. Кухня ожидает в OrderPaid поля event_id, order_id, total и currency. Монолит публикует total и currency вместе с существующим amount, чтобы остальные потребители продолжали получать сумму. Pact проверяет настоящий обработчик кухни и событие из Outbox, полученное после HTTP-оплаты.

`python -m pytest tests/contracts -v` запускает совместимую проверку и проверку намеренной несовместимости. Вторая удаляет total из события. Pact обнаруживает несовпадение, а тест подтверждает ожидаемый отказ верификатора. Пример сгенерированного контракта хранится в `pacts/kitchen-orders.json`.

## Нагрузка

Сценарий `locustfile.py` отправляет запросы с весами 7/2/1 — список меню, карточка блюда, создание заказа. Используется JWT отдельного тестового покупателя, пауза между действиями 1–3 секунды. Старый сценарий замера кеша сохранён в `locust_menu_baseline.py`.

Установите `requirements-load.txt`. В PowerShell подготовьте временный файл с access-токенами:

```powershell
$env:LOAD_FIXTURE = Join-Path ([IO.Path]::GetTempPath()) ('lab10-' + [guid]::NewGuid().ToString() + '.json')
try {
    docker compose exec -T app python -m scripts.prepare_lab10_load | Select-Object -Last 1 | Set-Content -Encoding utf8NoBOM -LiteralPath $env:LOAD_FIXTURE
    locust -f locustfile.py --host http://127.0.0.1:8000
} finally {
    Remove-Item -LiteralPath $env:LOAD_FIXTURE -ErrorAction SilentlyContinue
}
```

В интерфейсе http://localhost:8089 задайте сначала 50, затем 200 пользователей, spawn rate 10. Подготовлены 200 отдельных покупателей с тестовым балансом. Для прогонов создаются новые данные.

25 ноября 2026 года выполнены два 60-секундных прогона. CSV сохранены в `benchmarks/lab10_50_*` и `benchmarks/lab10_200_*`. На 50 пользователях получено 24,45 RPS, общий p95 94 мс, p95 создания заказа 210 мс. На 200 пользователях получено 82,77 RPS, общий p95 230 мс, p95 создания заказа 510 мс. HTTP-ошибок в обоих прогонах нет. В финальной консольной сводке Locust счётчики немного выше CSV из-за завершения запросов при остановке.

В проверенном диапазоне p95 не превысил секунду, порог появления 5xx не достигнут. Выявлено узкое место фоновой обработки — после прогонов в очереди Celery было 1640 задач. Каждый заказ создаёт три задачи с суммарным временем около четырёх секунд, а воркер имеет concurrency=2. Уже 2,76 заказа/с на первом прогоне создают задачи быстрее, чем воркер их выполняет. Из оставшейся очереди после проверки удалены только задачи нагрузочных заказов.

Prometheus подтвердил максимум занятых соединений API и загрузку CPU в `benchmarks/lab10_metrics.json`. Пиковая загрузка API составила около 0,8 ядра. Измерения относятся к локальному запуску и не определяют предельную производительность сервера.

## CI и защита ветки

Workflow `.github/workflows/tests.yml` запускается на push и pull_request. Обязательная проверка называется `required-tests`. Она устанавливает тестовые зависимости, проверяет существующие тесты API и сервисов, PostgreSQL через Testcontainers и контракт Pact. RabbitMQ в CI запускается сервисом GitHub Actions.

В репозитории [GhostASA5/sirius_food](https://github.com/GhostASA5/sirius_food) настроена защита main с обязательной проверкой `required-tests`, включая применение к администраторам. [PR № 1](https://github.com/GhostASA5/sirius_food/pull/1) содержит отдельный намеренно падающий тест для демонстрации красного CI. Он оставлен открытым для защиты работы. Проверки можно открыть во вкладке [Actions](https://github.com/GhostASA5/sirius_food/actions).

Локальный общий прогон завершился результатом 45 passed. Проверены совместимый контракт и ожидаемый отказ при удалении total, а также три интеграционные проверки на временной PostgreSQL. Общий tests/conftest.py задаёт тестовое окружение до импорта приложения, поэтому CI не зависит от локального .env.
